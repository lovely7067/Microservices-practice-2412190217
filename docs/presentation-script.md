## 第 2 页 · 项目概览（约 45 秒）

> 先说这个项目"做什么、用什么"。
>
> 业务上实现了三大核心流程：**会员登记**——手机号唯一，重复登记返回 409；**会员卡**——办卡之前必须先远程校验会员存在，支持有效期和次卡；**入场核验**——入场前校验是不是本人的卡、有没有过期、有没有剩余次数，通过后扣减次数写入场记录。
>
> 技术栈：Java 21 + Spring Boot 4.0 + Spring Data JPA，数据层是 MySQL，测试用 H2 内存库；交付用 Docker 多阶段构建和 Compose 一键编排；服务治理引入了 Nacos 做注册与发现。
>
> 整个项目有一条贯穿的原则，就是下面这行字：**单体版本始终保留可运行，每一步都可运行、可验证、可回退**——这也让我每个阶段出问题时都能退回到上一个稳定状态。

## 第 4 页 · 第 01–05 周成果：单体阶段（约 60 秒）

## 第 5 页 · 第 06 周成果：微服务拆分（约 60 秒）

> 第 6 周把单体按业务边界拆成三个服务：**member-service** 管会员档案，端口 8081；**card-service** 管会员卡，8082；**checkin-service** 管入场核验，8083。
>
> 三个服务遵守三条拆分原则：跨服务引用**只存 ID 不建外键**；数据库物理隔离，**三个库三个账号**，用 GRANT 控制权限，一个服务连不上别人的库；原来的单体保留在 monolith 目录，不删不改。
>
> 右边是调用链：入场请求到 checkin-service，它调 card-service 验卡；办卡时 card-service 调 member-service 校验会员。失败语义是明确的：会员或卡不存在返回 **404**；非本人卡、卡过期这些业务规则返回 **400**；依赖服务不可用返回 **503**。关键约束是：**校验不通过或者依赖不可用时，绝不写本地数据**，后面下线验证会专门证明这一点。

## 第 6 页 · 第 07 周成果：Nacos 注册与发现（约 60 秒）

> 第 7 周解决"服务地址写死"的问题。
>
> 左边是部署与注册：部署 Nacos Server **v3.2.4**，控制台在 18080——这是 Nacos 3 的新特性，控制台从服务端拆出来了，服务端 API 是 8848，SDK 走 9848 的 gRPC；鉴权开启，密钥放在本地 .env 不进仓库，数据用命名卷持久化。三个服务以各自的 spring.application.name 注册到分组 **GYM_YZ_GROUP**，实例全部 healthy。
>
> 代码改造的核心是：跨服务调用从"配置文件写死地址"改成**每次操作前调用 `DiscoveryClient.getInstances("服务名")` 实时解析实例**，拿到实例 URI 再拼原来的业务路径发请求；所有固定地址配置都删掉了。拿不到实例就返回 503，不会拿旧地址盲发。
>
> 右边是实测：全部正常时办卡返回 201；**下线 member-service 后**，实例被心跳摘除、列表为空，此时办卡返回 **503，而且数据库记录数不变**——证明了不会绕过校验写脏数据；**恢复后**大约 30 秒实例重新注册，同一个请求又返回 201。
>
> 这里还有一个容易混淆的点：Nacos 的 healthy 看 SDK 心跳，Actuator 的 health 看应用内部状态，Actuator DOWN 并不会让 Nacos 摘除实例，两个是独立的视角。

## 第 7 页 · 关键代码 ①：服务发现与跨服务调用（约 45 秒）

> 刚才说"每次操作都解析实例"，具体长什么样？左边是寻址的核心，就这几行：
>
> `resolve` 方法调用 `discoveryClient.getInstances(serviceId)` 拿当前实例列表——注意它是**在每次业务操作里被调用的**，不是启动时调一次存起来，所以对方重启换 IP、扩缩容都能感知。列表为空就抛 `RemoteServiceException`，全局异常处理会把它映射成 **503**，绝不会拿着旧地址盲发请求。最后取第一个实例的 URI 返回——只取第一个是本周明确的边界，注释里写清楚了，不做轮询、重试和熔断。
>
> 右边是调用方 `MemberClient`：目标服务名常量 `MEMBER_SERVICE_ID` 是 "member-service"，**和对方 `spring.application.name` 一致**；拿到实例 URI 后拼上原来的业务路径 `/api/members/{id}` 发请求。错误处理两行：对方返回 404 说明会员不存在，转成业务异常透传；连接失败或超时抛 503。**校验不通过就不写本地数据**，这在代码层就保证了。

【可略】老师如果问"为什么不用 OpenFeign"，回答：课程要求理解服务发现的底层过程，自己解析实例、拼 URL、处理错误码；Feign 只是这一步之上的封装，换 Feign 业务层不用动。

## 第 8 页 · 关键代码 ②：先验后写与超时配置（约 45 秒）

> 第二段代码看业务规则怎么保证数据干净。
>
> `createCard` 的**校验链顺序就是考点**：第一步先远程校验会员存在——刚才看到的 `getMember`，404 或 503 会直接中止流程；第二步是本地业务规则——结束日期必须晚于开始日期、次卡必须指定剩余次数，不满足抛 400；第三步，**全部通过才调 `save` 落库**。所以任何一步失败，数据库里都不会多出半截数据——这就是"先验后写"。
>
> 右边是 `RestTemplate` 的超时配置：连接 2 秒、读取 3 秒，从配置文件读、可以覆盖，作用是**防止被慢依赖拖垮自己**——不能因为 member-service 卡住，把 card-service 的线程也全部挂住。
>
> 三类异常 `NotFound`、`InvalidRequest`、`RemoteService` 统一由 `@RestControllerAdvice` 映射成 404、400、503，Controller 里一行 try/catch 都不用写。

## 附：可能被追问的问题 · 30 秒速答

| 问题 | 要点 |
| --- | --- |
| 为什么每次 getInstances，而不是启动时解析一次？ | 实例重启换 IP、扩缩容时缓存地址会失效；每次解析才能感知变化，且 Nacos 客户端有本地订阅缓存，不是每次都走网络 |
| 为什么用 RestTemplate 不用 OpenFeign？ | 课程要求理解服务发现底层过程（自己解析实例、拼 URL、处理错误码）；换 Feign 只是再封装一层，业务层不用动 |
| 404 和 503 的区别？ | 404 是依赖服务正常工作并告诉你资源不存在（业务错误，透传）；503 是依赖本身不可达（基础设施错误）。两者都不写本地数据 |
| 办卡校验通过后 member 数据变了怎么办？ | 存在事务窗口，本周方案是"先验后写 + 失败不写"，文档明确说明，不做自动补偿 |
| 两种健康的区别？ | Nacos healthy 来自 SDK 心跳（5s 一次），Actuator 检查应用内部（数据源等）；MySQL 挂了 Actuator=DOWN 但心跳还在，Nacos 不摘除实例 |
| 测试为什么不连真实 Nacos？ | 单测要快且稳定，关闭自动注册 + H2 + Mockito，任何机器 `mvnw test` 可复跑 |
| 为什么跨服务不建外键？ | 三库物理隔离外键跨不了库，引用完整性由调用时校验保证 |
| 只取第一个实例怎么办？ | 本周刻意的简化边界，代码里注释明确；改轮询只需改 resolver 一处 |
| 控制台为什么是 18080？ | Nacos 3.x 控制台从服务端拆出独立端口（容器内 8080），8848 只提供服务端 API，旧教程的 8848/nacos 是 2.x 用法 |
| 复跑验证的命令？ | `docker compose up -d --build` 后 `bash scripts/smoke-test.sh`，7 项全过退出码 0 |
