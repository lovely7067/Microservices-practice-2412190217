# 项目选题记录

## 1. 最终选题

**椰汁健身房管理系统**

## 2. 选题确定过程

在选题初期，我考虑了多个候选方向，包括“图书借阅系统”、“餐厅点餐系统”和“健身房会员系统”。

- **排除图书借阅系统**：虽然业务逻辑清晰，但整体业务场景较为单一，多角色协同和复杂事务场景较少，后续演进空间有限。
- **排除餐厅点餐系统**：虽然涉及支付和订单，但业务重点偏向于即时性点餐，缺乏长期会员关系维护的维度。
- **最终确定椰汁健身房管理系统**：该系统具有鲜明的多用户角色（会员、教练、管理员），业务逻辑上包含了“预约-签到-扣费”这样典型的状态流转和事务场景。同时，课程容量控制、教练排班冲突检测等需求，非常适合在后续课程中引入并发控制、分布式锁和消息通知机制。此外，该系统贴近生活，需求明确，易于进行数据库设计和微服务拆分。

## 3. 选题思考

本选题完全满足课程要求：具备明确的业务背景、多个用户角色以及足够丰富的功能模块。在后续课程任务中，可以无缝接入数据库持久化、服务拆分、认证、消息、事务、监控和部署等全套企业级开发技术栈。


## 功能规划

### 1. 本周完成内容

本周作为课程项目的启动阶段，重点完成了从选题到功能边界的完整规划，具体包括：

- **项目选题确定**：经过多方向对比（图书借阅、餐厅点餐、健身房系统），最终确定“椰汁健身房管理系统”为本学期持续演进的唯一项目。
- **业务背景与目标用户梳理**：明确了项目解决的实际问题（传统健身房管理低效），并划分出 **会员、教练、管理员** 三类核心用户角色及其需求。
- **功能模块设计**：完成了五大核心模块的初步规划，包括 **用户中心、课程与排班、预约与签到、会籍与订单、数据统计**，并明确了每个模块包含的具体功能。
- **核心业务流程梳理**：以“会员预约课程”为主线，梳理了从浏览课程、名额校验、锁定名额、发送通知、现场签到到数据归档的完整业务闭环。
- **项目边界界定**：明确了当前项目范围（需求分析、数据库设计、核心 CRUD、基础认证）以及暂不实现的内容（真实支付、硬件对接、多租户 SaaS 化）。
- **演进方向规划**：制定了后续在 **认证、服务拆分、消息、事务、监控、部署** 六个维度的技术演进路线。

### 2. 后续计划

基于本周的功能规划，后续将按以下阶段逐步推进：

1. **阶段一（数据库设计）**：完成核心业务实体（用户、会员、教练、课程、预约、订单）的 ER 图设计，并建立数据库表结构。
2. **阶段二（核心功能实现）**：完成用户中心、课程管理、预约与签到模块的基础 CRUD 接口开发，实现数据库持久化。
3. **阶段三（服务拆分与认证）**：将单体应用按业务边界拆分为微服务，引入 JWT + Spring Security 实现多角色认证授权。
4. **阶段四（消息与事务）**：引入消息队列处理预约通知，使用分布式事务保证“扣费+预约”的一致性。
5. **阶段五（监控与部署）**：引入 Prometheus + Grafana 监控服务健康度，使用 Docker + Kubernetes 完成容器化部署。
